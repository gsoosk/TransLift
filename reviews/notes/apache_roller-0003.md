# apache_roller-0003

## Velocity-template reads on model objects, missed entirely (not just the model.init() gap calibration already flags)

Calibration already notes that the extractor never dispatches into `Model.init`/pager getters called by name from `.vm` templates. This batch shows the gap is broader than the ModelLoader-dispatched models: a servlet can also put a manager object directly into the Velocity context with `model.put(...)` and let the template call manager methods on it by reflection, with no `Model.init`/`ModelLoader` indirection at all, and the extractor has no way to see that either.

- PlanetFeedServlet.doGet (key `13926f9ba68b`): `model.put("planet", planet)` (PlanetFeedServlet.java:103) puts the `PlanetManager` itself in the model; `templates/planet/planetrss.vm:32/34-35` then calls `$planet.getEntries(...)`, `$planet.getGroup(...)`, `$planet.getWeblogger(...)` directly. `getEntries` (JPAPlanetManagerImpl.java:299-340) runs a JPQL query against `SubscriptionEntry` (table `rag_entry`, SubscriptionEntry.orm.xml:25) that has no Java call site anywhere in the servlet — the extractor's 3-op draft had no inkling of it.
- FeedServlet.doGet (`03388cbba3b0`), PageServlet.doGet/doPost (`b6053ea1a124`, `ca7103a082c2`), PreviewServlet.doGet (`e26fcf7a4705`): these do go through `ModelLoader.loadModels` (the gap calibration already names), but the concrete read that was missing in every case was the same one — `FeedModel`/`PageModel`/`PreviewPageModel`.`getWeblogEntriesPager()`, called by the theme template (`themes/basic/weblog.vm:24`, `weblog-entries-rss.vm:39`) and answered by a pager whose constructor eagerly runs the query (`WeblogEntriesListPager.java:87` / `WeblogEntriesLatestPager.java:65`) against `WeblogEntry` (table `weblogentry`).

Likely cause, same as the already-reported gap: txscan only walks the explicit Java call graph from the declared root; it has no model for Velocity's `$obj.method(...)` reflection dispatch, whether the object reached the template via `ModelLoader`/`Model.init` or via a bare `model.put(...)`. Not asking for a third fix round since both rounds are used; recording the extra `model.put` case here because the calibration text, read literally, only describes the `ModelLoader`-dispatched half of the gap.
